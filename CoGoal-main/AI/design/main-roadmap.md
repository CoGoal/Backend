# CoGoal-main: следующие домены

Это план работы по [OpenAPI](../../../docs/api/openapi.yaml), а не описание готового кода. Реализованное состояние и общие ограничения находятся в [main-service.md](main-service.md). Контракт содержит будущее поведение нескольких сервисов; путь из OpenAPI не означает, что вся операция должна быть реализована в main.

## Последовательность реализации

| Блок | Статус | Основные зависимости |
| --- | --- | --- |
| Приватный профиль и редактирование имени/аватара | Реализовано | JWT, события аккаунта auth |
| Публичный профиль, категории и фонды | Не реализовано | Пользовательские данные main, справочники |
| Цели и этапы | Не реализовано | Автор, категория, фонд, бизнес-модель пакта |
| Приглашения, отклики и участники пакта | Не реализовано | Цели, поиск пользователя по username, состояния участия |
| Жизненный цикл пакта и расторжение | Не реализовано | Участники, отчёты; платёжная часть зависит от отдельного payment-сервиса |
| Отчёты, доказательства и проверка этапов | Не реализовано | Этапы, права участников, хранение файлов |
| Монеты, достижения, магазин, чат и поддержка | Не реализовано | События бизнес-доменов и правила из соответствующих разделов контракта |
| Интеграции payment и email | Сервисы ещё не перенесены/не созданы в текущем backend | Отдельный дизайн и согласованный формат межсервисных событий |

Это порядок по зависимостям. Очередной запрос пользователя определяет конкретный блок, а не обязанность реализовать всю таблицу за одну задачу.

## Цели и этапы: первый крупный блок main

Маршруты контракта: GET/POST /goals, GET /goals/my, GET/PATCH/DELETE /goals/{goalId}, операции /goals/{goalId}/milestones. Общий префикс — /api/v1.

Сущности для проектирования: Goal, Milestone, Category, Charity, Pact и PactParticipant. Их физическая схема ещё не создана. Сначала сопоставь поля CreateGoalRequest, Goal и Milestone с требованиями, затем добавь Hibernate-сущности, репозитории и Liquibase.

Подтверждённые контрактом правила:

- Автор определяется по JWT. Дедлайн цели находится в будущем; дедлайны этапов не позже дедлайна цели.
- Создание цели вместе с этапами и связанным пактом выполняется как единая бизнес-операция.
- Редактирование цели и этапов разрешено автору до активного пакта. Активный пакт ограничивает изменение и удаление; ошибки и коды берутся из OpenAPI.
- Публичная лента исключает собственные цели, цели с активным пактом и цели с ожидающим персональным приглашением. Фильтры, пагинация и сортировки определены контрактом.
- InviteUsername при создании цели влияет на приглашение и видимость ленты. Поэтому реализация создания цели не должна молча игнорировать это поле, даже если приглашения выделены в следующий блок.

API сейчас описывает создание пакта вместе с целью, а состояние цели и участие в пакте тесно связаны. Перед первым changeset нужно определить их связь и переходы по контракту. Список полей ERD в описании OpenAPI — заметки к проектированию, а не уже существующие таблицы.

## Приглашения и пакты

Разделы контракта: Invitations и Pacts. Пользователя для приглашения ищем по проекции username в main; auth остаётся владельцем логина. Учитывай задержку обновления этой проекции.

Контракт задаёт персональное приглашение, отклик из ленты, принятие/отклонение, максимум пять участников и автоматическое отклонение приглашения через 48 часов. Переходы состояний и права участников следует проектировать вместе: два параллельных принятия приглашений не должны превышать лимит, повторный запрос не должен создавать второе участие.

Письмо о приглашении относится к будущей интеграции email-сервиса. Текущие письма auth для сброса пароля и смены email не являются реализацией уведомлений main. Формат событий для email пока не согласован; не считай его существующим контрактом.

## Платежи и отчёты

Main хранит бизнес-условия целей и пактов. Вызовы платёжного провайдера, платёжные webhook и учёт платёжных операций требуют отдельного дизайна payment-сервиса. Не превращай местный баланс монет в подтверждение реального платежа. Суммы контракта — десятичные значения, без float/double; формат API определён OpenAPI.

CheckIns описывает отправку доказательств выполнения этапа и проверку напарником. Доступ должен учитывать принадлежность этапа пакту и участие пользователя. Количество попыток, сроки и автоматические переходы берутся из контракта и требований. Files отдельно описывает загрузку доказательств, аватаров и скриншотов; сейчас профиль хранит только avatarUrl, загрузчик не реализован.

## Как фиксировать очередной дизайн

Для выбранного блока достаточно описать владельца данных, Hibernate-сущности и связи, разрешённые переходы состояний, границы транзакций, HTTP-ошибки и события для соседних сервисов. Отдельно отметь вопросы, на которые нет ответа в текущем контракте. Неблокирующие детали реализации можно решить по существующему устройству main; новые бизнес-правила не следует выдавать за согласованные требования.

После реализации обнови статус блока и ссылки на код. Не дублируй весь OpenAPI: подробные DTO, маршруты и ответы поддерживаются в исходном контракте.
