# CoGoal-main: ответственность и устройство

## Границы сервиса

Main отвечает за профиль пользователя и бизнес-функции CoGoal: цели, этапы, участие в пактах и связанные с ними операции. Auth отвечает за вход и учётные данные. Gateway маршрутизирует внешний HTTP-трафик, Eureka предоставляет обнаружение сервисов. Межсервисные события передаются через Kafka. Базы сервисов разделены; main не читает и не изменяет таблицы auth напрямую.

Текущая рабочая среда использует Neon: main_db для main и auth_db для auth. Подключения задаются в игнорируемом .env отдельно для каждого сервиса. Включён дополнительный docker-compose.neon.yml; локальный PostgreSQL не требуется для запуска. Настройки и возврат к локальному режиму описаны в README backend.

Принятые решения: пользовательские ID — BIGINT/Java Long; единое поле login при входе принимает email либо username; имя и аватар принадлежат main. Документы со старым UUID не отменяют эти решения.

## Владение данными

| Данные | Где изменяются | Что хранится в main |
| --- | --- | --- |
| Логин username | Auth, отдельный метод смены логина | Копия для отображения и поиска, обновляемая событием |
| Email | Auth, смена с подтверждением письмом | Копия для приватного профиля |
| Роль | Auth | Копия в профиле; права запроса определяются проверенным JWT |
| Пароль, refresh и одноразовые токены, блокировка входа | Auth | Не передаются и не хранятся |
| Имя и avatarUrl | Main | Основные данные профиля |
| Монеты и дата создания профиля | Main | Сохраняются при синхронизации аккаунта |
| Цели, этапы, пакты, участники, отчёты | Планируется в main | Таблицы и операции пока не реализованы |

Смена логина идёт через gateway сразу в auth, без HTTP-пересылки из main. Наличие users в пути не определяет владельца данных. GET auth/me возвращает аккаунт без имени и аватара; GET users/me возвращает профиль main.

UUID сохраняются в идентификаторах событий Kafka и legacy-ссылках для миграции. Их нельзя путать с ID пользователя и менять на Long только ради одинакового типа всех идентификаторов.

## Что реализовано

| Метод через gateway | Поведение |
| --- | --- |
| GET /api/v1/users/me | Приватный профиль по ID из проверенного JWT |
| PATCH /api/v1/users/me | Изменение имени и avatarUrl; возвращает профиль |

Оба метода требуют access-токен. При ещё не доставленной регистрации профиль отвечает 404 PROFILE_PENDING. PATCH отклоняет username и другие неизвестные поля с 400. Пропущенный avatarUrl сохраняет аватар, явный null удаляет его. Баланс и дата создания от PATCH не меняются.

Достижения и статистика в ответе пока являются заглушками. Публичные профили, цели, пакты, операции с монетами, отчёты, магазин и поддержка описаны в OpenAPI, но в текущем main ещё не реализованы. HelloController — технический остаток шаблона, а не бизнес-функция.

## Структура кода

Базовый пакет: edu.stankin.cogoalmain.

| Пакет / каталог | Назначение |
| --- | --- |
| web/controllers | REST-контроллеры, валидация HTTP-входа, GlobalExceptionHandler |
| pojo/dto | DTO запросов и данных; сохранено выбранное пользователем расположение |
| service | Бизнес-операции и транзакции |
| db/entity | Hibernate-сущности |
| db/repo | Spring Data JPA-репозитории |
| config/security | Цепочка безопасности и проверка JWT |
| kafka/config, kafka/event, kafka/consumer | Настройки брокера, формат событий и слушатель |
| src/main/resources/db | Liquibase master и changeset |

Существующие реализации: [ProfileController](../../src/main/java/edu/stankin/cogoalmain/web/controllers/ProfileController.java), [ProfileService](../../src/main/java/edu/stankin/cogoalmain/service/ProfileService.java), [UserProfile](../../src/main/java/edu/stankin/cogoalmain/db/entity/UserProfile.java), [UserProfileListener](../../src/main/java/edu/stankin/cogoalmain/kafka/consumer/UserProfileListener.java).

Main работает через Hibernate и репозитории. SQL в Liquibase и тестах схемы допустим; возвращать бизнес-операции main на JdbcTemplate не соответствует выбранному устройству. Контроллеры получают проверенного пользователя и вызывают сервисы. Сервисные операции, меняющие связанные данные, определяют границу транзакции.

Новые таблицы создаются добавлением changeset в [Liquibase master](../../src/main/resources/db/db.changelog-master.xml). Уже применённые changeset сохраняют свои checksums. Hibernate настроен на validate; он не создаёт схему вместо миграций. Времена обрабатываются в UTC; текущая настройка Hibernate для Instant согласована с TIMESTAMP существующей схемы.

## Проверка JWT и прав

SecurityConfig извлекает Bearer-токен и устанавливает Long ID в контекст. JwtConfig проверяет подпись HS256, срок действия, issuer, audience и обязательные claims. Main проверяет токен локально общим с auth ключом; HTTP-запрос в auth для каждого обращения не нужен.

ID текущего пользователя берётся из AuthenticationPrincipal, а не из произвольного поля тела запроса. Для будущих целей и пактов потребуется отдельно проверять владение и участие: корректный JWT сам по себе не даёт право изменять чужую цель. Роль в сохранённом профиле не заменяет проверенную роль запроса.

Auth после выхода отзывает refresh-токены. Уже выпущенный access остаётся действующим до истечения срока; текущая реализация main не использует список немедленно отозванных access-токенов.

## Синхронизация через Kafka

Auth сохраняет задачу outbox в одной транзакции с аккаунтом, затем публикует событие. Main обрабатывает его и подтверждает Kafka-запись после commit Hibernate. Подтверждение публикации auth и обработка main — разные этапы.

События UserRegistered и UserProfileUpdated имеют eventId, schemaVersion, occurredAt и снимок аккаунта. ID пользователя — Long, ключ Kafka — его десятичная строка. Новая схема — 2; схема 1 поддерживается для старых очередей и миграций. Изменения аккаунта схемы 2 не содержат имени и аватара. Начальное имя передаётся событием регистрации; временный payload auth outbox очищается после подтверждения брокера.

Инварианты обработчика:

- При первом создании профиля начальные монеты начисляются один раз. Значение берётся из INITIAL_COINS.
- Новая версия аккаунта обновляет email, username и роль; старая или повторная версия не откатывает их.
- События не перезаписывают имя и аватар уже инициализированного профиля, баланс и дату создания.
- Поздняя регистрация может заполнить начальное имя, даже если версия аккаунта уже выше. Явное редактирование профиля в main имеет приоритет.
- Для этого используется profile_initialized отдельно от profile_version. PATCH профиля не повышает версию аккаунта auth.
- Синхронизация и PATCH используют одну блокировку по пользовательскому ID. Это сохраняет результат при параллельной работе слушателя и HTTP-запроса.

Ошибочные JSON, неподдерживаемые схемы и конфликты отправляются в DLT. Для остальных ошибок настроены две повторные попытки перед DLT. Offset проблемного события подтверждается только после успешной записи в DLT; восстановление требует устранения причины и повторной доставки.

Имена топика и группы задаются конфигурацией. По умолчанию: cogoal.user-profiles.v1 и cogoal-main-profiles-v1. В Compose брокер доступен сервисам на kafka:29092.

## Проверка изменений

Для обычных изменений main достаточно его релевантных тестов. Изменение формата событий требует проверки совместимости с auth и старой схемой, изменение маршрутов — проверки gateway. Сценарии профиля должны учитывать повторные события, порядок регистрации и обновления, сохранение баланса, аватара и пользовательского имени.

Рабочие команды находятся в [README backend](../../../README.md). smoke_auth проверяет внешний сценарий через gateway и Mailpit; smoke_kafka временно останавливает локальные main и Kafka и восстанавливает их. Это тесты локальной Compose-среды, а не команды для произвольного рабочего окружения.
