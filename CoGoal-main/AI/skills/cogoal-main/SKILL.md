# Работа с CoGoal-main

Используй этот скилл для реализации и изменения main. Он не задаёт самостоятельную задачу на создание payment, email или frontend и не заменяет прямые указания пользователя.

## Контекст по задаче

Прочитай [описание сервиса](../../design/main-service.md). Для нового домена открой соответствующий блок [плана](../../design/main-roadmap.md) и его DTO/маршруты в [OpenAPI](../../../../docs/api/openapi.yaml). Сверь реализованное поведение с исходниками, прежде чем обещать наличие метода. План не является готовым кодом.

Принятые границы: main владеет именем, аватаром, балансом и бизнес-данными; auth — логином, email, паролем и безопасностью. Username меняется в auth; main получает проекцию через Kafka. Прямого доступа к БД другого сервиса нет. Пользовательские ID — Long/BIGINT; внутренние eventId и legacy-ссылки могут быть UUID.

Дизайн и документацию пиши по [правилам понятного текста](../plain-writing/SKILL.md).

## Реализация

Опирайся на выбранное устройство main: сущности и Spring Data JPA-репозитории в db, транзакции в service, DTO в pojo/dto, REST и GlobalExceptionHandler в web/controllers, интеграция событий в kafka. Пользователь определяется по проверенному JWT; для бизнес-операций дополнительно проверяются владение и участие.

Изменения схемы оформляй новым Liquibase changeset, не переписывая уже применённые миграции. Если меняется HTTP-контракт, обнови OpenAPI и проверь маршрут gateway. Сохраняй существующие данные при миграции. В main таблица legacy_user_profiles пока участвует в переносе старого баланса; архивные таблицы auth уже удалены после проверки переноса.

При изменении Kafka-профилей сохраняй отдельные версии аккаунта и инициализацию профиля. Повторные/старые события не начисляют монеты второй раз и не меняют имя или аватар, отредактированные в main. Поздняя регистрация не откатывает актуальный логин. Новая схема событий и старые очереди должны быть совместимы при обновлении сервисов.

Для нового бизнес-блока сначала определи связи, состояния и границы транзакций по контракту, затем реализуй выбранные операции. Если отсутствие бизнес-правила мешает корректному результату, сформулируй конкретное противоречие; не расширяй задачу новыми правилами незаметно.

## Проверка и поддержка контекста

Запусти проверки, соответствующие изменению: права на чужие данные, валидация, переходы состояний, миграции существующих записей, повторная обработка событий или конкурентные операции — по затронутой логике. Команды и особенности локальных smoke-тестов находятся в [README backend](../../../../README.md).

Обнови реализованное состояние в design и кратко сообщи, что изменилось, чем проверено и что осталось запланированным. Не объявляй работающим весь main только потому, что соответствующие операции перечислены в OpenAPI.
